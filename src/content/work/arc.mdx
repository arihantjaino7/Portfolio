decision:
  question: Where does the anti-cheat live?
  chose: Postgres triggers and row-level security
  rejected:
    - Validation inside Next.js server actions
    - A trusted backend service placed in front of the database
  why: >-
    Supabase hands the browser its own key and lets it talk to PostgREST directly.
    That means any rule I enforce in application code is a rule a competitor can skip
    by opening a terminal — server actions and a gatekeeper service both assume the
    only caller is my code, and neither assumption survives contact with a motivated
    user who wants to backdate an entry. Moving day locks and rule immutability into
    triggers and RLS makes the check unconditional: the database refuses the write
    whether the request came from the app, from curl, or from the Supabase dashboard.
    The cost is real — policies are harder to read than a TypeScript guard, and the
    test suite has to reach the database to mean anything — and that cost is why the
    suite exists.

Scores are computed in the competitor's own timezone, not the server's, so a day
boundary means the same thing for everyone in a league. Rule sets are versioned rather
than mutated: a score always resolves against the version that was in force on the day
it was earned, which makes retroactively fixing a losing result structurally
impossible rather than merely discouraged.

The blind-mode reveal holds standings back until a configured point in the
competition. It is a product decision with a schema consequence — the rankings have to
be computable and withheld, not simply uncomputed.
