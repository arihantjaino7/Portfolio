problem: >-
  Asking one model to research a topic gets you a report written from training data —

  writing model see the topic alone: every sentence it writes descends from a page
  Tavily actually returned, through a summary you can open and read.

decision:
  question: What does the writing model actually see?
  chose: Five independent per-source summaries, never the five raw pages
  rejected:
    - All five sources concatenated into one report prompt
    - A single search-and-write call with the pages as tool output
  why: >-
    Tavily's advanced search returns full page content, and five of those concatenated is
    a long, wildly uneven prompt — the longest page dominates it and a short, dense source
    gets skimmed, purely because of length. Summarising each source in its own call gives
    every source the same weight in the final report no matter how long the original page
    was, and it leaves an artifact behind: when the report says something that looks wrong,
    there is a specific summary to open and a specific source behind that summary. The cost
    is real and worth naming — six model calls per topic instead of one, and a slower run.
    The alternative is a report that is cheaper to produce and impossible to audit.

The graph is deliberately linear — `search → summarize → report → END` — because nothing
in the task branches. A state machine earns its keep here not through routing but through
the shared `ResearchState`: each node returns only the field it owns, so what every stage
contributed stays separately inspectable after the run.

Summarisation is the one place the loop is sequential rather than concurrent. Five sources
at one Groq call each is the obvious thing to parallelise next, and the state shape already
allows it — the summaries list is built from the results list and nothing downstream cares
about the order they arrive in.
